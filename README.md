# 外部疑似装置 Next

集合住宅システム向けのシリアル通信シミュレータです。既存の
`external-device-simulator-desktop`、`serialApp`、VB6版「外部疑似装置」の長所を統合し、
提供された通信仕様書を正として電文生成・受信検証・通信手順・異常試験を実装しています。
アイホンの仕様書6冊に加え、パナソニックの警報プロトコル4種とエレベータ連動にも対応しています。

## 設計上の改善

- COMポートの読み取り元をElectronメインプロセスの1か所に限定しています。
- 送信をキューで直列化し、UI処理とACK待ちが同じ受信データを奪い合わない構成です。
- 長さ、BCC、区切り、文字種、Version、送信方向を検証してからACK／NAKを返します。
- 受信チャンクの任意分割・連結に対応し、BCCがSTX／ETX等と同値でも誤認しません。
- 受信のフレーム境界検出は機種別リーダーへ集約し、マンションコントローラはLEN範囲・ETX位置・BCCまで検証するデコーダへ委譲しています。
- 相手装置としての自動応答は、通信仕様で応答内容が確定するものだけを送信し、業務データが必要な要求は理由をログに残して送信しません。
- 警報の発信情報は、選択した発信種別と割付パターンに対応する警報名（火災、非常、ガス漏れ、防犯、外出／在宅警戒など）をbit1〜bit8に表示し、チェックとHEXが双方向に同期します。仕様上使えないbitはチェックできず、HEX直接入力で立てた場合は注意として表示します。
- 宅配・非接触キー・パナソニック警報の各画面に「受信モニタ」を備え、受信電文をSTX／ID／データ長／各データ桁／ETX／BCCへ分解し、位置・HEX・意味を表で表示します。
- 受信モニタはBCC異常や長さ違反でも読み取れた桁を必ず表示し、仕様違反は「仕様違反」、機種制約の超過や方向の食い違いは「注意」として区別します。
- 2線式は全ロッカーを連続送信する相手が多いため、住戸アドレス単位で最新状態を集計する「住戸別の受信状況」を備え、受信履歴の保持件数を超えても登録済みの住戸が未登録ロッカーに埋もれません。集計した住戸はまとめて登録一覧へ反映できます。
- 受信内容はロッカー一覧の現在状態、2線式の登録行、非接触キーの送信フォームへワンクリックで反映でき、折り返し試験に使えます。
- 受信履歴は電文のバイト列で保持するため、対象システムや動作側を切り替えると過去の受信電文もその条件で読み直せます。
- 宅配ボックスの登録データは旧VB6版と同じ一覧表で編集でき、居室番号を範囲指定で一括設定できます。
- 2線式の住戸アドレスは「住戸番号の登録数の連番」という規定どおりロッカー番号から自動採番し、入力させません。
- 待機処理は非同期で、ACK待ち中も画面をブロックしません。
- 各画面の入力値・通信条件・異常条件をこのPCへ保存、またはJSONで共有できます。
- パナソニックのエレベータ連動は正常応答が10H／30Hの2種類で、NAKに相当する応答がありません。検証できない電文には応答せず、相手の再送を待ちます（30Hは`0`と同値のため、電文の外側でだけ制御コードとして扱います）。
- 警報は、受信した電文だけからメーカーとプロトコルを判定します。アイホンQ49-023GとパナソニックHPC／TSSはSTX＋データ長37H＋データ7byte＋ETX＋加算BCCという外形が同じで長さやBCCでは見分けられないため、発信種別の台帳・棟番号の符号化・発報元の割付といった中身の規定から絞り込みます。一意に決まれば選択中のプロトコルを自動で切り替え、決められないときは候補と「どちらで読むと何になるか」を受信モニタへ示します。選択と違う形式の電文も受信できるよう、STX形式とレコード形式を1つのリーダーで読みます。
- パナソニックは1画面で4プロトコルを切り替え、電文形式・通信条件（HPC／TSSは1200,E,8,1、大興／リモートは1200,N,8,1）・入力欄・受信リーダーがまとめて追従します。
- 大興／リモートのアンサーバックは伝送制御コードではなく電文で届くため、制御コード待ちとは別の待ち行列で受け取り、NAKまたは5秒無応答で計3回まで再送します。
- 通信ログはメインプロセスが受信した時刻で記録し、保持件数は2,000／20,000／100,000件から選べます。
- 試験中の誤操作でログを失わないよう、リロード用のキー操作を無効化し、接続したままの終了時は確認します。
- Electronはcontext isolation、sandbox、CSPを有効にし、外部遷移と新規ウィンドウを拒否します。

## 起動

開発環境ではNode.js LTSとnpmを用意し、次を実行します。

```powershell
npm install
npm start
```

または `起動.bat` を実行します。画面上部でCOMポートと通信プリセットを選び、対象装置の画面で電文をプレビューしてから送信してください。

## 検証と配布ビルド

```powershell
# プロトコル、異常系、DOM契約、構文
npm test

# 実Electronでpreload・全画面・全モジュールの初期化を確認
npm run test:smoke

# Windows x64 portable版
npm run dist:win
```

配布ファイルは `dist/external-device-simulator-next-<version>-x64.exe` に生成されます。

### バージョンの確認

画面左上のアプリ名の下と、「概要」画面の「バージョン情報」にバージョンが出ます。
配布版ではビルド日時とコミットも表示され、起動時の通信ログ（READY行）にも同じ内容が残ります。
不具合の報告時は「バージョン情報をコピー」で以下の形式を取得できます。

```
external-device-simulator-next v1.1.0 / 2026-08-25 09:45:04（55e2206） / Electron 43.4.0 / Chromium 150.0.7871.224 / Node 24.18.1 / win32-x64
```

ビルド日時とコミットは `npm run stamp`（`pack` と `dist:win` が自動で実行）が `build-stamp.json`
へ書き出し、electron-builder がEXEへ同梱します。開発実行（`npm start`）では生成されないため、
ビルド欄は「開発実行」と表示されます。コミットに `+` が付く場合は、未コミットの変更を含むビルドです。

### アプリアイコン

アイコンの原本は `build/icon.svg`（16/24px用の簡略版は `build/icon-small.svg`）です。
`build/icon.ico` と `build/icon.png` は次のコマンドで再生成します。

```bash
npm run icons   # 要: librsvg2-bin, imagemagick
```

**ImageMagick(`convert`)でSVGを直接ラスタライズしてはいけません。** 内蔵SVGレンダラは
`stroke="url(#gradient)"` を解釈できず、グラデーション指定のストローク（枠線・コーナー
飾り・シェブロン）を黙って捨てるため、ほぼ真っ黒な角丸四角形だけのICOが生成されます。
ファイル自体は正常に見えるため気付きにくく、実際に一度この不具合を踏んでいます。
ラスタライズは必ず `rsvg-convert` で行ってください（`npm run icons` はこれを保証します）。

`npm test` の `icon-asset` テストがICOを画素単位で検証し、アクセント色が欠落した
アイコンがコミットされることを防ぎます。

## 通信条件（ボーレート等）が分からないとき

「通信設定」画面の**通信条件の判別**は、条件を順に切り替えて実際に受信し、
どの設定なら仕様どおりのフレームとして読めるかを確かめます。対応機器で使う8通り
（約30秒）と、標準ボーレート全16通り（約60秒）から選べます。判別中は接続を切り、
相手からの送信を待つため、**相手が自発的に送信する状態**（警報の発生など）にしてから
実行してください。見つかった条件はボタン1つで通信設定へ反映できます。

受信はできているのに解釈できない電文には、受信モニタが偏りから当たりを付けます。

| 受信データの特徴 | 示すこと |
|---|---|
| 1バイトあたりのビット変化が少なく、00Hの割合が高い | 設定しているボーレートが相手より**速い** |
| ビット変化が多いのに、電文長より短い | 設定しているボーレートが相手より**遅い** |
| 電文長に対して約N倍に伸びている／縮んでいる | ずれの倍率の目安（候補ボーレートを提示） |

ここで分かるのは**ずれの向きと目安**までです。ボーレートが違うとUARTはスタートビットを
誤った位置で拾うため、受信バイト列から元の波形は復元できません（ランレングスからの
直接推定は実測でも精度が出ませんでした）。正確な特定には上記の判別を実行してください。

## プロトコル判定でわかること・わからないこと

受信電文から一意に特定できるのは、そのプロトコルにしかない要素を含む場合です。

| 判定できる根拠 | 特定されるプロトコル |
|---|---|
| 発報元が管理室（0C）・集合玄関（0D）・共用部 | アイホン Q49-023G |
| 棟番号がBCDで64H以上（例：70H＝70棟） | アイホン Q49-023G |
| 発信種別 05H（汎用警報情報）・10H（住戸情報要求） | HPC |
| 住戸番号の上位4bitが0以外（ヒストリー応答） | HPC |
| 発信種別 02H（警報情報３） | HPC または TSS（アイホンにはない） |
| 棟番号がBCDとして不正（例：0AH＝10棟） | HPC または TSS（アイホンはBCD） |
| 警報No.40（宅配登録･削除） | リモート |
| 定時送信（`TRS!7`） | リモート |

次の電文は仕様が共通なため、電文だけでは区別できません。この場合は切り替えず、
候補と読みの違いを示します（プロトコルによって同じバイト列の意味が変わるため）。

- 発信種別 00H・01H … アイホン・HPC・TSS のすべてで成立
  （例：警報情報①の bit1 は「火災、遠隔試験」、HPC/TSS の bit0 は「火災」）
- 発信種別 44H（警戒解除） … アイホン と TSS で成立
- 発信種別 30H（ヒストリー要求） … アイホン と HPC で成立
- 発信種別 04H … アイホン・HPC・TSS で成立
- 警報No.40 を含まないレコードとアンサーバック … 大興 と リモート で成立
  （例：警報No.03 は大興なら「非常」、リモートなら「防犯(代表)」）

アイホンと判定された電文はパナソニック画面では送受信できないため、自動では切り替えず
「警報（アイホン）」画面で確認するよう案内します。逆に「警報（アイホン）」画面で
Q49-023Gとして読めない電文を受けたときは、通信ログの理由へ判定結果を添えます。

## 仕様上の注意

- TSSの発信種別一覧(p.1)には00H／01H／04H／44Hしか載っていませんが、同仕様p.2には02H（警報情報３）のビット割付があります。本実装はp.2を正として02Hも扱い、その旨を発信種別の注記として保持しています。
- パナソニックの棟番号はHEX値がそのまま棟数を表すバイナリで、0AHが10棟、63Hが99棟です。アイホンQ49-023GのBCD（10棟＝10H）とは異なるため、両者を取り違えないよう別の符号化として実装しています。
- 大興とリモートは警報No.03／04の割付が入れ替わっています（大興は03＝非常・04＝防犯(代表)、リモートは03＝防犯(代表)・04＝非常）。各仕様書の別表どおりに持ち、プロトコルを切り替えると表示も切り替わります。
- リモートの定時送信は物件コードの桁数が規定されていません。「リモート送信機にて設定、IFUでは使用／参照しない」とあるため、入力文字列をそのままETXまでのデータとして載せ、受信側もETXまでを物件コードとして読みます。
- パナソニックのエレベータ連動は、共同玄関解錠(IK)の付加コードによって住戸を特定できるかが変わります。管理室(01)・暗証番号(02)による解錠では棟番号・住戸番号が仕様上の固定値のため、入力欄を無効にし、受信時に値が入っていれば仕様違反として表示します。
- 非接触キーID情報(SB)の付加コードは仕様書で■■と書かれ内容の規定がないため、2桁の数字を直接指定できるようにしています。
- HPCの再送上限は仕様上MAX256回ですが、送信FSMが扱えるのは255回までのため255回で試験し、その旨を通信ログへ残します。
- Q49-023G p.20の「警戒設定」例はBCCが`3E`と印字されていますが、同仕様p.13の規定式では`41`です。本実装は規定式を正として`41`を生成し、`3E`は不正BCCとして扱います。
- Q49-023G p.11の警戒解除情報パターン３はbit1が「外出警戒設定」と印字されていますが、同表のパターン１「警戒解除」・パターン２「外出警戒解除」および5.2.4の趣旨から解除側の誤記と判断し、画面表示は「外出警戒解除」としています。電文のビット位置と値は変わりません。
- VB6版に含まれるベンダー固有・基板試験系機能の一部は、対応する通信仕様やソースが提供されていません。根拠のない互換実装は行わず、現時点では汎用ターミナルと異常注入で調査可能にしています。
- 実機固有のUSBシリアルドライバ、配線、衝突タイミングは、対象ハードウェアを接続した結合試験が必要です。
- 現在のportable EXEは評価用の未署名ビルドです。社外配布や本番運用では組織のコード署名証明書を設定してください。
